# 《学的是史》微信小程序：端到端开发任务树 v2.0

> 用途：交给本地 Coding Agent 作为长期执行清单。  
> 原则：从 0 开始，先完成可运行、可测试、可上线的垂直闭环，再逐步叠加复杂交互。  
> 任务状态建议：`[ ] 未开始`、`[-] 进行中`、`[x] 已完成`、`[!] 阻塞`。

---

# 0. Agent 执行规则

## 0.1 每次只领取一个“最小可验收任务”

每次开始编码前，Agent 必须先输出：

```text
本次任务：
依赖是否满足：
涉及文件：
计划修改：
验收方式：
风险点：
```

完成后必须输出：

```text
已完成内容：
新增或修改文件：
如何本地验证：
仍未解决的问题：
建议领取的下一个任务：
```

## 0.2 禁止事项

- 不允许一次性生成整个项目。
- 不允许在没有 Mock 数据的情况下直接接真实云数据库。
- 不允许在基础页面未打通前先做人物星图、二维时间轴、实时 PK。
- 不允许为了“以后可能用到”提前引入复杂状态管理、微服务或多端框架。
- 不允许把密钥、AppSecret、云函数私密配置写入仓库。
- 不允许未经确认修改已经验收通过的公共组件行为。

## 0.3 Definition of Done：每个任务的完成标准

每个任务至少满足：

- 页面可以在微信开发者工具中正常编译。
- 没有明显控制台报错。
- 空数据、加载中、加载失败三种状态均有处理。
- 至少提供一个手动验收路径。
- 核心逻辑有最小单元测试或可重复验证脚本。
- README 或任务记录中标记完成情况。

# 2. 技术方案冻结

## 2.1 推荐技术栈

```text
客户端：微信原生小程序 + TypeScript
UI：优先使用原生组件；必要时按需引入 TDesign Miniprogram
后端：微信云开发 / CloudBase
数据：云数据库
文件：云存储
服务端逻辑：云函数
音频：小程序音频能力 + 云存储音频 URL
复杂可视化：Canvas 2D，先独立 Demo 后集成
版本控制：Git + GitHub
文档：README.md + TASKS.md + CHANGELOG.md + docs/
```

## 2.2 为什么先使用原生小程序

- 项目第一目标是微信小程序，不是多端发布。
- 原生组件与微信运行时适配更直接。
- 对 Canvas、音频、登录、云开发等能力的排查路径更短。
- Vibecoding 时减少跨框架封装层，降低 Agent 误改概率。
