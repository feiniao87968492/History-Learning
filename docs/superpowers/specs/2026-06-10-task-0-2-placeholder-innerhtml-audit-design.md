## 5. 占位文案审计设计

### 5.1 审计目标

搜索当前项目中所有 `showToast(...)` 调用，筛出包含以下关键词的调用点：

- `开发中`
- `加载中`
- `即将上线`
- `功能`

这里的“功能”按计划要求执行搜索，但记录时只保留真实具有“占位/未完成提示”语义的调用点。

### 5.2 审计范围

默认审计运行时相关代码文件：

- `index.html`
- `src/js/**/*.js`

测试文件、历史备份文件和计划文档不纳入正文清单。

### 5.3 记录格式

每个调用点建议使用统一条目格式：

```md
- 文件：`index.html`
  - 调用：`showToast('手机号登录功能开发中')`
  - 功能：登录页手机号登录按钮
  - 分类：占位入口
```

实际写入时应保持单层列表风格，可压缩成单条描述，例如：

```md
- `index.html`：`showToast('手机号登录功能开发中')`，用于登录页手机号登录按钮，分类为“占位入口”。
```

### 5.4 分类规则

占位文案调用点采用以下分类：

- `占位入口`：用户点击入口后仅弹出“开发中/加载中/即将上线”等提示
- `状态提示`：与真实功能流程相关，但仍使用“加载中/功能中”等临时状态提示
- `说明性提示`：不是入口占位，而是辅助说明；仅在明确具有占位语义时纳入

若一个调用点同时满足多个分类，以最贴近用户可见行为的分类记录。

### 5.5 不纳入清单的情况

以下情况不记入“占位文案审计结果”正文：

- 计划文档中的示例文字
- 测试用例中的 mock 文案
- 非 `showToast` 路径上的普通文本
- 不具备占位语义的正常成功/失败提示

## 6. innerHTML 审计设计

### 6.1 审计目标

搜索当前仓库中所有 `innerHTML` 使用点，并判断其写入内容的来源类型。

### 6.2 审计范围

默认审计运行时相关文件：

- `index.html`
- `src/js/**/*.js`

测试文件不纳入审计正文。

### 6.3 记录格式

每个 `innerHTML` 使用点使用统一条目格式：

```md
- `src/js/noun.js`：用于渲染相关名词按钮，来源分类为“外部 JSON / 外部数据”。
```

若某个使用点明显同时拼接多种来源，仍只记录一个主分类，并在简短备注中说明“混合来源”。

### 6.4 来源分类规则

`innerHTML` 使用点统一归入以下四类之一：

- `用户输入`
- `外部 JSON / 外部数据`
- `存储数据`
- `内部常量 / 模板`

#### `用户输入`

当 `innerHTML` 拼接内容直接或间接来自用户输入框、评论、帖子、表单输入时，归为此类。

#### `外部 JSON / 外部数据`

当写入内容来自 `fetch` 加载的 JSON、运行时外部数据对象或同类外部输入时，归为此类。

#### `存储数据`

当写入内容来自 `localStorage` 或通过存储读取后再渲染的持久化内容时，归为此类。

#### `内部常量 / 模板`

当写入内容完全由代码内固定模板、常量字符串或受控静态结构拼接而成时，归为此类。

### 6.5 混合来源判定规则

若一个 `innerHTML` 使用点同时含有多种来源，按**最高风险来源优先**记录，优先级如下：

1. `用户输入`
2. `外部 JSON / 外部数据`
3. `存储数据`
4. `内部常量 / 模板`

例如：

- 若模板里既有固定 HTML，也拼接用户输入，则归为 `用户输入`
- 若模板里既有常量，又拼接 JSON 数据，则归为 `外部 JSON / 外部数据`

### 6.6 备注规则

每条 `innerHTML` 记录允许加一句简短备注，用于说明用途，例如：

- “用于渲染影视榜单列表”
- “用于渲染收藏空状态”
- “用于渲染相关名词按钮”

备注只能说明用途，不写整改方案。

## 8. 信息采集规则

### 8.1 以真实搜索结果为准

所有条目必须来自实际搜索命中，不得凭印象补充。

### 8.2 以当前工作区为准

审计基于当前工作区内容，包括用户已确认视为项目现状的现有变更。

### 8.3 运行时文件优先

正文清单优先覆盖运行时文件：

- `index.html`
- `src/js/**/*.js`

测试、历史备份、计划文档可以在搜索时辅助判断，但不进入正式审计章节。

### 8.4 分类必须稳定

同一类来源在全篇必须保持同一命名，不允许一处写“外部数据”，另一处写“JSON 数据”而不加统一定义。

### 8.5 事实与判断分离

调用点、用途、来源分类可以写入；整改优先级、修改建议、解决方案不写入本任务正文。

## 9. 边界与一致性规则

### 9.1 审计不等于修复

`Task 0.2` 的完成标准是“清单准确”，不是“问题已解决”。

### 9.2 保持与 Task 0.1 共存

新章节应以追加方式写入 `docs/current-state.md`，不破坏已建立的基线结构。

### 9.3 允许记录事实性风险类别

虽然本任务不写整改方案，但“来源分类”“占位入口分类”属于可复核的审计信息，可以记录。
