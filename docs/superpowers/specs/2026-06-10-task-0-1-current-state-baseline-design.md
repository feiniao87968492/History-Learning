# 学的是史 Task 0.1：仓库现状基线文档设计

## 1. 背景与目标

当前仓库已经完成一部分静态原型拆分工作，但真实状态仍分散在多个位置：

- 页面结构主要集中在 `index.html`
- 一部分业务逻辑已迁移到 `src/js/*.js`
- 仍存在较大段内联脚本
- 数据文件已从早期少量 JSON 扩展到多份内容型数据文件
- 测试、资源目录、历史计划文档也在持续增加

Phase 1 计划中的 `Task 0.1` 要求先建立一份**可供后续任务复用的仓库基线文档**，用于回答以下问题：

1. 当前项目到底有哪些页面和主要 UI 容器
2. 当前已经拆出了哪些 JS 模块，各自负责什么
3. 当前有哪些 JSON 数据文件
4. `index.html` 里还保留了哪些内联脚本区域
5. 当前对外暴露了哪些 `window.xxxAPI`
6. 当前项目已使用了哪些 LocalStorage key

本次设计目标是定义 `docs/current-state.md` 的内容边界、组织方式和采集规则，使其成为一份**事实性基线清单**，而不是问题审计或整改方案。

## 2. 设计范围

本次设计只覆盖 `Task 0.1` 对应的基线文档产出，不进入后续任务。

### 2.1 本次范围内

`docs/current-state.md` 需要记录以下内容：

1. 页面与主要页面容器
2. 现有 JS 模块及职责
3. 数据文件清单
4. `index.html` 中内联脚本现状
5. 已暴露的 `window.xxxAPI`
6. 已识别的 LocalStorage key
7. 少量事实性备注，帮助新开发者快速建立全局认知

### 2.2 明确不在本次范围内

以下内容不写入 `Task 0.1` 文档正文：

- `showToast('开发中')` 等占位入口审计清单
- `innerHTML` 风险点审计
- XSS、安全整改建议
- adapter 改造方案
- 文件重构建议
- 功能缺陷列表
- TODO 清单或实施计划

这些内容属于 `Task 0.2` 及之后的任务，不应提前混入基线文档。

## 3. 方案选择

本次选用：**最小基线清单型文档**。

### 3.1 选定方案

文档只记录“仓库现状事实”，不写审计结论与整改建议。

组织方式采用“技术层分段 + 必要事实备注”的形式，便于后续任务按章节补充引用。

### 3.2 选择理由

该方案最符合 `Task 0.1` 的边界：

- 能直接满足“让新开发者读懂现状”的目标
- 不会和 `Task 0.2` 的审计工作重叠
- 后续可在同一文档中新增“审计结果”章节，而不必推翻现有结构
- 对 Coding Agent 也更友好，后续查找页面、模块、key、接口时有固定索引位置

### 3.3 未采用方案

#### 方案 A：基线清单 + 风险分析

这种方案看似一步到位，但会提前进入 `Task 0.2`，导致任务边界模糊。

#### 方案 B：完整现状报告

如果同时包含现状、问题、建议和整改方向，文档会过重，不利于后续增量维护，也不符合本轮“仅基线清单”的确认结果。

## 4. 输出文件设计

### 4.1 输出文件

- 新建：`docs/current-state.md`

### 4.2 文档定位

该文件是仓库当前状态的**基线索引文档**，不是设计文档、任务计划、审计报告或变更日志。

它的主要读者有两类：

1. 新进入项目的开发者或 Agent
2. 后续执行 `Task 0.2-1.6` 的实施者

### 4.3 写作原则

文档应满足以下要求：

- 以事实描述为主，不写“应该”“建议”“后续将”
- 尽量使用清单化结构，便于扫描
- 仅记录当前仓库真实存在的内容
- 若计划与仓库现状冲突，以仓库现状为准
- 对重要现状允许增加一行备注，但备注也必须是事实性表述

## 5. 文档结构设计

建议 `docs/current-state.md` 使用以下结构：

### 5.1 项目概览

简要记录：

- 当前项目定位
- 当前技术栈
- 页面入口文件
- 主要代码目录

该部分只帮助读者建立初始心智模型，不展开实现细节。

### 5.2 页面与主要容器

列出当前页面与主要页面容器，包括但不限于：

- `.page` 级页面
- `.sub` 级子页面
- 弹层、面板、详情容器

每项建议记录：

- 容器 `id`
- 页面性质（主页面 / 子页面 / 弹层 / 面板）
- 当前主要用途

目的不是列出所有 DOM 节点，而是说明“有哪些页面单元在承载功能”。

### 5.3 JS 模块与职责

列出 `src/js/` 下当前已存在的模块文件，并记录每个模块的主要职责。

每项建议记录：

- 文件路径
- 对外暴露的 API 名称（如存在）
- 当前已承担的功能范围

如模块与 `index.html` 中残留内联脚本存在职责交叉，可在备注中写明“部分逻辑已迁移，仍存在内联残留”，但不写整改方案。

### 5.4 数据文件清单

列出 `src/data/` 下当前 JSON 文件，按文件名逐项记录：

- 文件路径
- 当前数据主题
- 被哪个页面或模块使用，若已知可注明

目的在于建立“数据面”的总体视图，便于后续 `validate-data.js` 和数据驱动渲染改造。

### 5.5 `index.html` 内联脚本现状

该章节记录 `index.html` 中仍保留的主要内联脚本区域。

这里不需要逐行抄录代码，而是按“功能块”归纳，例如：

- 页面切换
- 热点筛选
- 影视榜单与待看栏
- 人物关系图
- 思维导图
- 讨论区
- 打卡签到

每块只需说明：

- 大致位置
- 主要功能
- 是否已存在对应外部模块

该章节的目的，是让后续任务快速识别“哪些逻辑还在 HTML 内联脚本里”。

### 5.6 已暴露的 `window.xxxAPI`

单独汇总当前仓库已暴露的全局 API。

每项建议记录：

- API 名称
- 来源文件
- 主要职责

该章节要和“模块列表”分开，原因是后续 adapter 和全局兼容层改造会频繁引用这份索引。

### 5.7 已识别的 LocalStorage key

汇总当前代码中已经实际使用到的 LocalStorage key。

每项建议记录：

- key 名称
- 来源模块或位置
- 当前用途

若某个 key 同时出现在模块和内联脚本中，也只按当前事实记录，不在本任务中判断优劣。

### 5.8 当前状态备注

只允许记录少量事实性总结，例如：

- 当前项目处于“部分模块化、部分内联脚本保留”的过渡状态
- 已存在若干测试文件，但测试尚未全绿
- 数据文件数量已超过早期 README 中的最小版本描述

该章节不是问题清单，而是帮助读者快速把握当前仓库成熟度。

## 6. 信息采集规则

为保证 `docs/current-state.md` 准确且可复核，采集时应遵循以下规则。

### 6.1 只记录真实存在的仓库内容

不得根据计划文件推测内容是否“应该存在”。

例如：

- 若文件存在，则记录
- 若 API 已在代码中暴露，则记录
- 若计划中提到但仓库中不存在，则不写入基线文档

### 6.2 以当前工作区为准

本轮基线文档以当前工作区可见文件为准，包括用户已明确要求视为项目现状的现有变更。

### 6.3 优先记录“已存在的职责归属”

若同一功能同时存在于模块文件和 `index.html` 内联脚本，应如实写明当前的双重状态，不做“谁才是正确实现”的判断。

### 6.4 LocalStorage key 必须来自真实代码搜索

不能只凭命名约定推断 key，必须以代码中实际出现的 key 为准。

### 6.5 API 名称必须来自真实暴露

只有真正写入 `window.xxxAPI = { ... }` 或兼容挂载到 `window.xxx = ...` 的接口才纳入清单。

## 7. 边界与一致性规则

### 7.1 文档不承担整改职责

`docs/current-state.md` 的作用是“建立现状基线”，不是“推动整改”。

### 7.2 文档可服务后续任务

虽然本任务不做审计，但文档结构应便于后续在其基础上追加章节，例如：

- 占位文案审计结果
- `innerHTML` 审计结果
- adapter 接入进度

### 7.3 文档应允许与 README 共存

README 偏对外介绍，`docs/current-state.md` 偏内部现状索引。二者角色不同，不要求内容完全一致。

## 8. 验收标准

当以下条件全部满足时，`Task 0.1` 可视为完成：

1. `docs/current-state.md` 已创建
2. 文档可被新开发者快速读懂
3. 文档包含以下最小信息集：
   - 页面与主要容器
   - JS 模块与职责
   - JSON 数据文件
   - `index.html` 内联脚本位置
   - `window.xxxAPI`
   - LocalStorage key
4. 文档内容以当前仓库现状为准，无明显推测性描述
5. 文档没有提前混入 `Task 0.2` 的审计结论或整改建议
