# 学的是史静态内容拆分与 resources 统一管理设计

## 1. 背景

当前项目已经完成第一轮原生静态站拆分：

- `index.html` 已外链 CSS 与大部分 JS 模块
- `src/js/` 已存在 `app.js`、`noun.js`、`timeline.js`、`podcast.js`、`film.js`、`favorites.js`、`checkin.js`、`ai-assistant.js` 等模块
- `src/data/` 已存在 `nouns.json`、`timeline.json`、`podcasts.json`、`films.json`、`rankings.json` 等数据文件

但项目仍处于“半拆分、半内联”的过渡阶段，主要问题包括：

- `index.html` 中仍保留大量静态展示内容
- `index.html` 末尾仍保留一段较大的内联脚本，包含业务静态数据与页面交互函数
- 一部分静态内容已经进入 JSON，一部分仍硬编码在 HTML 或脚本中，边界不统一
- 仓库中已有 `resources/` 目录，但内部结构混乱，包含系统垃圾文件、平台残留目录与不稳定命名，不适合作为长期统一资源目录

因此，本次需要在不破坏现有页面效果与交互的前提下，继续推进静态内容拆分，并建立统一、可维护的 `resources/` 资源目录规范。

## 2. 本次目标

本次设计聚焦两条主线：

### 2.1 静态内容继续拆分

将当前散落在 `index.html` 静态 HTML 与内联脚本中的展示型静态内容继续迁移到 `src/data/` 下的 JSON 文件中，由现有 JS 模块或 `app.js` 中的页面初始化逻辑进行加载和渲染。

### 2.2 统一资源目录管理

以 `resources/` 作为项目唯一的统一媒体资源目录，整理图片、图标、音频等文件资源的归档方式、命名规则与引用路径，并清理其中的垃圾文件和无效目录。

## 3. 非目标

本次明确不包含以下内容：

- 不引入前端框架或构建工具
- 不重写现有交互方式
- 不强制去除所有内联 `onclick`
- 不大规模改造页面 DOM 结构
- 不进行 UI 改版
- 不要求一次性统一所有 JSON 的数据风格
- 不建立复杂 CMS 或后台内容管理系统
- 不把所有零散 toast 文案抽成独立的全局文案中心

## 4. 总体策略

本次采用**保守增量式拆分**策略。

核心原则如下：

1. `index.html` 继续保留为页面骨架层
2. `src/data/` 继续作为结构化内容数据层
3. `resources/` 作为真实文件资源层
4. `src/js/` 中现有模块继续承担渲染与交互职责
5. 优先抽离“明显就是数据”的内容，不优先重写页面结构
6. 每次改动都应可单独验证、可局部回退

这意味着本次工作不是一次性把页面改造成完全配置驱动系统，而是在当前已存在的拆分架构上继续推进，让内容与资源逐步退出 HTML 和内联脚本。

## 5. 目标目录结构

### 5.1 数据目录

继续使用现有目录：

```text
src/data/
```

该目录只存放结构化内容数据，不存放图片、音频等二进制资源。

### 5.2 资源目录

统一以：

```text
resources/
```

作为项目资源根目录。

建议目标结构为：

```text
resources/
  images/
    memes/
    nouns/
    people/
    timeline/
    common/
  audio/
    podcasts/
  icons/
  raw/
    imported/
```

含义如下：

- `images/`：前端页面实际引用的图片资源
- `audio/`：前端页面实际引用的音频资源
- `icons/`：独立图标资源
- `raw/`：原始导入素材、尚未清洗或尚未进入正式页面引用的文件

## 6. 需要拆分的数据范围

### 6.1 已有数据文件，继续保留

以下文件继续作为正式数据层使用：

- `src/data/nouns.json`
- `src/data/timeline.json`
- `src/data/podcasts.json`
- `src/data/films.json`
- `src/data/rankings.json`

如本次改造需要，可在不破坏调用方的前提下补充字段，例如图片路径、标签或分组信息。

### 6.2 建议新增的数据文件

本次新增或补齐以下数据文件：

- `src/data/memes.json`
  - 首页轮播梗图数据
  - 包含标题、说明、标签、图片或封面引用信息
- `src/data/hot-articles.json`
  - 首页热点文章、推荐内容与分类信息
- `src/data/people.json`
  - 人物关系网核心数据、资料卡信息、事迹、年表、评价
- `src/data/discussions.json`
  - 讨论区默认帖子与评论假数据
- `src/data/science-tools.json`
  - 科学备考页面功能卡片配置
- `src/data/mindmaps.json`
  - 思维导图默认节点结构与分组信息
- `src/data/profile-menu.json`
  - “我的”页面菜单项配置
- `src/data/feedback-types.json`
  - 反馈弹窗中的标签选项

### 6.3 本轮不强制新增的文件

以下内容可保留在代码中，不强制本轮抽离：

- 全站零散 toast 文案
- 极少量只出现一次、且不构成复用价值的占位文案
- 纯交互控制状态

## 7. 拆分优先级

为降低风险，本次拆分按以下顺序推进。

### 第一批：明显属于数据对象的内容

优先抽离：

- 首页梗图数据（当前内联脚本中的 `memeData`）
- 人物关系网数据（当前内联脚本中的 `peoData`）
- 讨论区默认帖子数据
- 科学备考入口卡片
- 反馈类型配置

这一批内容天然适合 JSON 化，改造收益高，且对页面结构影响最小。

### 第二批：大块静态展示列表

在第一批稳定后，再抽离：

- 首页热点文章区域
- 名词页初始卡片区域
- 播客列表初始卡片区域
- 人物页默认展示列表
- “我的”页面菜单项

这一批可以显著减轻 `index.html` 中的静态内容密度。

### 第三批：与资源目录强关联的内容

在数据结构稳定后，再逐步引入统一资源引用，例如：

- 人物头像
- 名词配图
- 梗图配图
- 播客封面
- 时间轴相关配图
- 影视封面

这一阶段的重点是让 JSON 中的图片、音频路径统一指向 `resources/`。

## 8. 各层职责划分

### 8.1 `index.html`

继续承担：

- 页面骨架
- 容器结构
- 弹层、面板、挂载点节点
- 外部 CSS / JS 引用

不再继续承载：

- 大段业务静态列表内容
- 大块业务数据对象

允许暂时保留：

- 必要的内联 `onclick`
- 少量无法立即移除的静态壳层节点

### 8.2 `src/data/`

负责保存：

- 可结构化维护的业务展示内容
- 页面卡片配置
- 人物资料与关系数据
- 讨论区假数据
- 可复用的页面内容块

不负责保存：

- 图片二进制
- 音频二进制
- 纯交互运行态

### 8.3 `resources/`

负责保存：

- 页面实际引用的图片、图标、音频等资源文件
- 待清洗的原始素材

### 8.4 `src/js/`

负责：

- 加载 JSON
- 渲染页面内容
- 绑定交互
- 调用现有模块能力
- 处理加载失败兜底

## 9. JS 改造策略

本次不以“重新设计整个 JS 模块体系”为目标，而是尽量复用现有结构。

### 9.1 `app.js`

继续作为总入口，负责：

- 加载新增 JSON 数据
- 调度页面级初始化
- 做容错与兜底
- 暴露仍需兼容的全局函数

### 9.2 保持现有业务模块职责

保留以下模块现有职责方向：

- `noun.js`
- `timeline.js`
- `podcast.js`
- `film.js`
- `favorites.js`
- `checkin.js`
- `ai-assistant.js`
- `navigation.js`

### 9.3 页面级逻辑处理方式

对于首页、人物页、讨论区、思维导图等目前仍主要依赖内联脚本的区域，本轮优先采用以下策略：

- 将相关静态数据抽到 `src/data/`
- 将对应渲染逻辑迁入 `app.js` 中按功能分区管理
- 暂不强制为每个页面新建独立 JS 文件

原因是：当前阶段重点是内容拆分与资源统一，而不是模块体系大重构。

后续如页面逻辑继续增长，可再考虑补拆：

- `home.js`
- `people.js`
- `discuss.js`
- `mindmap.js`

但这不是本次必做项。

## 10. 资源目录规范

### 10.1 运行时资源与原始素材分离

正式页面引用文件放入：

- `resources/images/`
- `resources/audio/`
- `resources/icons/`

非正式、待整理、外部导入原件放入：

- `resources/raw/imported/`

这样可以避免页面运行资源与素材堆混在一起。

### 10.2 路径稳定

页面和 JSON 中应尽量使用稳定、可预测的路径，例如：

- `resources/images/memes/qinshihuang.jpg`
- `resources/images/people/wuzetian.jpg`
- `resources/audio/podcasts/zhenguan.mp3`

### 10.3 命名建议

正式页面资源建议采用：

- 小写英文
- 连字符或下划线风格保持一致
- 避免系统自动生成名、乱码名、含平台垃圾前缀的文件名

### 10.4 数据中只保存引用路径

数据文件中仅保存最终引用路径，不把目录推导规则写死在 JS 中。例如：

```json
{
  "image": "resources/images/people/wuzetian.jpg"
}
```

## 11. 资源清理要求

本次应清理或隔离以下非正式资源：

- `__MACOSX/`
- `.DS_Store`
- `Thumbs.db`
- 无意义缓存或平台残留目录
- 不适合直接作为前端正式引用路径的乱码文件名

如果某些原始资源当前还不能安全改名，应至少先移入 `resources/raw/imported/`，避免继续污染正式引用目录。

## 12. 数据结构建议

本次不要求全项目所有 JSON 风格完全一致，但应遵守以下局部一致性原则：

- 列表型内容优先使用数组
- 详情型内容可使用对象映射
- 若某模块已稳定依赖某种结构，优先兼容现有调用方式
- 新增字段以满足当前页面渲染为目的，不过度超前建模

例如：

- `people.json` 可采用数组或对象映射，但必须方便按人物名或 id 定位
- `discussions.json` 应以数组形式表示帖子列表
- `hot-articles.json` 应支持分类字段，以便首页筛选使用

## 13. 错误处理与兼容要求

### 13.1 JSON 加载失败容错

新增数据文件后，加载逻辑必须满足：

- 控制台可定位错误来源
- 页面不因单个 JSON 失败而整体崩溃
- 必要时使用空数组、空对象或最小 fallback
- toast 提示应尽量克制，不因多个文件失败而重复刷屏

### 13.2 页面兼容性

必须尽量保持：

- 页面视觉效果基本不变
- 页面入口和主要点击行为基本不变
- 现有 `id` / `class` 尽量稳定
- 现有全局函数兼容出口尽量保留

### 13.3 演进兼容性

后续继续拆分时，应优先在已有数据与目录规则上扩展，而不是再次推翻：

- `src/data/` 继续承载内容数据
- `resources/` 继续承载文件资源
- `app.js` 继续作为入口调度

## 14. 实施阶段建议

推荐将实现拆成三个阶段：

### 阶段一：数据抽离

- 把 `memeData`、`peoData`、讨论区数据等抽出到 JSON
- 在 `app.js` 中接入加载与渲染
- 减少内联脚本中的业务数据量

### 阶段二：页面静态列表改造

- 把首页热点、科学备考、人物默认块、“我的”菜单等改为数据驱动渲染
- 让 `index.html` 更多保留空容器和页面壳层

### 阶段三：资源目录整理

- 建立 `resources/` 目标层级
- 迁移正式页面资源
- 清理垃圾文件与无效目录
- 更新 JSON 或渲染逻辑中的资源引用路径

这一顺序可以让数据层先稳定，再统一资源路径，避免路径与数据结构同时大改造成联动风险。

## 15. 验收标准

### 15.1 内容拆分验收

- 主要静态展示内容已从 HTML / 内联脚本迁移到 `src/data/`
- `index.html` 中的大块业务静态内容显著减少
- 内联脚本中不再保留大型业务数据对象

### 15.2 资源目录验收

- `resources/` 成为统一正式资源目录
- 正式资源目录结构清晰
- 垃圾文件和平台残留被清理或隔离
- 资源引用路径稳定且可预测

### 15.3 运行验收

- 页面视觉基本保持不变
- 原有主要交互基本保持不变
- 无新增阻断性控制台错误
- 单个 JSON 文件加载失败不会拖垮整站

## 16. 设计结论

本次推荐采用“保守增量式静态内容拆分 + `resources/` 统一资源管理”方案：

在保留 `index.html` 页面骨架、保留现有原生 JS 模块体系与兼容全局函数出口的前提下，将散落在 HTML 与内联脚本中的展示型静态内容继续抽离到 `src/data/`，同时以 `resources/` 作为唯一正式媒体资源根目录，建立清晰的子目录层级、路径规则与清理规范，从而降低后续维护成本，并为后续进一步模块化打下稳定基础。
