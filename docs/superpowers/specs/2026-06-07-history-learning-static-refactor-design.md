# 学的是史静态原型拆分重构设计

## 1. 背景与目标

当前项目 `学的是史` 是一个可直接运行的中国历史学习网站原型，核心实现集中在根目录 `index.html` 中。该文件同时承载页面结构、样式、交互逻辑和大量静态内容，已经具备原型验证价值，但维护成本高、修改风险大，不利于继续扩展。

本次工作的目标不是升级技术栈，也不是重写产品，而是在保持原型视觉和交互基本不变的前提下，将单文件原型拆分为清晰、可维护的原生 Web 项目结构。

本次设计必须满足以下边界：

- 页面视觉效果基本不变
- 已有交互功能基本不变
- 不引入前端框架
- 不安装 npm 依赖
- 不迁移到微信小程序工程
- 不重写业务逻辑
- 每一步可回退
- 重构完成后仍可通过静态服务器直接运行

## 2. 设计原则

### 2.1 兼容优先

本次重构以兼容性为第一优先级。优先保证现有页面能继续显示、现有按钮能继续工作、现有交互不因结构优化而失效。所有拆分动作都应围绕“把内容移出去而不是把行为改掉”进行。

### 2.2 最小必要重构

本次只做为可维护性服务的拆分与清理，不借机做功能升级、界面改版、交互改写或工程化升级。能不动的结构尽量不动；必须调整时，仅处理明显错误、明显重复或会阻碍拆分的问题。

### 2.3 结构清晰但不过度现代化

拆分后项目应拥有明确的 HTML、CSS、JavaScript 与 JSON 数据边界，但不要求一步到位迁移成组件化、模块打包或框架化项目。此次目标是把原型从“难维护的一坨”整理成“可维护的原生静态项目”。

### 2.4 静态运行能力保留

重构后必须仍可通过静态服务器直接运行。由于后续会通过 `fetch` 加载 JSON，项目运行方式将从“双击 HTML”转为“启动本地静态服务器访问”。

## 3. 现状判断

当前项目结构非常简洁，主要文件为：

- `index.html`
- `skills/repositories.md`
- `skills/split.md`

其中 `index.html` 是明显的单文件原型，包含：

- 一整块内联 `<style>`
- 一整块内联 `<script>`
- 大量 `onclick="..."` 内联事件
- 多页面模拟切换结构
- 多类弹窗、面板、浮层和交互模拟

这说明当前项目与 `repositories.md` 中描述高度一致，适合采用“保守拆分、兼容优先”的重构方案。

## 5. 架构设计

### 5.1 HTML 层

根目录 `index.html` 在重构后主要承担页面骨架职责：

- 保留页面结构
- 保留现有页面容器与关键 `id`
- 保留主要 DOM 层级
- 引用外部 CSS 文件
- 引用外部 JavaScript 文件
- 保留少量暂时无法迁移的内联内容

本次不主动大改页面结构，不大规模删除节点，也不大规模重命名 `class` 或 `id`。这样可以降低样式选择器与交互逻辑失效的概率。

### 5.2 CSS 层

CSS 按职责拆分为三类文件：

#### `src/css/base.css`

负责基础样式与全局规则，例如：

- reset
- `body`
- `.page`
- 通用布局
- 通用颜色
- 通用按钮基础样式
- toast
- 通用面板基础能力

#### `src/css/components.css`

负责可复用组件样式，例如：

- 底部导航
- 卡片
- 搜索框
- 标签
- 弹窗
- 面板
- 收藏按钮
- AI 浮动按钮与对话面板
- 播客播放器
- 人物资料卡
- 笔记面板

#### `src/css/pages.css`

负责具体页面级样式，例如：

- 登录页
- 首页
- 名词解释页
- 时间轴页
- 科学备考页
- 思维导图页
- 人物专题页
- AI 播客页
- 影视书目页
- 收藏夹页
- 我的页面

拆分 CSS 时，不应为了整洁而重命名选择器。若发现完全重复的 CSS 定义，可在不改变最终表现的前提下合并，并在 `docs/refactor-report.md` 中记录处理情况。

### 5.3 JavaScript 层

JavaScript 按功能拆分，但保持当前原型所需的全局可调用特征。

#### `src/js/storage.js`

职责：

- 封装 `localStorage`
- 提供 JSON / string 读写工具
- 兼容旧存储 key
- 支撑登录状态、收藏、签到、设置等本地状态

#### `src/js/navigation.js`

职责：

- 登录后页面显示
- 主页面切换
- 子页面打开关闭
- 面板与弹窗开关
- toast 展示
- 底部导航联动

这是页面壳层控制模块。

#### `src/js/noun.js`

职责：

- 加载名词数据
- 渲染名词卡片
- 搜索名词
- 打开和关闭名词详情
- 收藏名词
- 分享名词
- 处理相关名词跳转

#### `src/js/timeline.js`

职责：

- 朝代切换
- 历史事件渲染
- 时间轴图表区域更新
- 上一朝代 / 下一朝代
- 缩放与拖拽
- 时代特征详情弹窗

#### `src/js/podcast.js`

职责：

- 播客列表展示
- 分类筛选
- 播放器开关
- 播放状态模拟
- 进度条与倍速逻辑
- 播客收藏

本次仍保持模拟播放器定位，不接入真实音频服务。

#### `src/js/favorites.js`

职责：

- 统一管理各类收藏
- 收藏夹页面渲染
- 收藏类型筛选
- 删除收藏项
- 与存储模块协作持久化数据

#### `src/js/ai-assistant.js`

职责：

- AI 助手面板开关
- 快捷问题处理
- 用户输入
- 模拟回复
- 聊天消息渲染
- AI 悬浮按钮拖拽

本次不接入真实 AI API，仅保留模拟交互。

#### `src/js/app.js`

职责：

- 作为应用入口
- 控制初始化顺序
- 触发 JSON 数据加载
- 协调各模块初始化
- 恢复本地状态
- 向 `window` 暴露 HTML 内联事件仍需要调用的函数

`app.js` 负责“编排”，而不是承担全部业务逻辑。

### 5.4 数据层

本次将适合结构化维护的内容抽离到 JSON 文件：

- `src/data/nouns.json`
- `src/data/timeline.json`
- `src/data/people.json`
- `src/data/podcasts.json`
- `src/data/books.json`
- `src/data/memes.json`

抽离原则如下：

- 优先抽离结构稳定、重复渲染明显的数据
- 不强迫一次性把所有静态文案都变成 JSON
- 数据格式优先为页面现有展示服务，而非提前为复杂后台建模
- 数据加载失败时允许 fallback，避免整站初始化崩溃

## 6. 兼容策略

### 6.1 保留全局函数出口

当前 HTML 大量使用 `onclick="..."` 调用函数，因此本次不强制把所有内联事件改写为 `addEventListener`。对应做法是：

- 模块内部保留正常函数定义
- 在 `app.js` 中把仍被 HTML 直接调用的函数暴露到 `window`

例如：

- `window.showToast = showToast`
- `window.openSub = openSub`
- `window.closeSub = closeSub`

这样可以最大程度减少因拆分脚本导致的功能回归。

### 6.2 保留 DOM 标识稳定性

本次不主动调整：

- 关键页面 `id`
- 关键 `class` 命名
- 现有主要按钮行为

CSS、HTML、JS 当前高度耦合，若拆分时同时进行大量命名重构，会显著增加页面失效风险。

### 6.3 保留 LocalStorage 兼容性

若现有原型已经使用 `localStorage` 记录状态，本次应优先保持旧 key 可用。若必须做数据结构整理，可通过兼容读取或温和迁移实现，而不是直接清空已有本地数据。

## 7. 错误处理设计

### 7.1 JSON 加载错误容错

后续通过 `fetch` 加载 JSON 时，可能出现路径错误、服务未启动、文件缺失或 JSON 格式错误。设计要求如下：

- 控制台输出明确错误信息
- 页面使用 toast 给出轻提示
- 关键模块可以使用最小 fallback 数据
- 某个数据模块失败时，不应拖垮整个站点初始化

### 7.2 初始化分层

初始化不应写成单一巨型过程，而应分为：

1. 基础页面能力初始化
2. 本地状态恢复
3. JSON 数据加载
4. 业务区域渲染
5. 可选增强能力初始化

这样能让单个模块出错时，其它基础功能仍尽可能可用。

### 7.3 问题修复范围控制

本次允许修复以下明显问题：

- 重复 CSS 定义
- HTML 标签闭合问题
- HTML 内联事件引用了不存在的函数
- 明显的路径错误
- 阻断性的控制台报错

但不借此扩展范围去做：

- 页面改版
- 全量结构重写
- 文案全面重写
- 技术栈升级

## 9. 文档与交付要求

除代码拆分外，还应补齐以下文档：

- `README.md`：说明静态服务器运行方式和项目结构
- `docs/refactor-report.md`：记录本次重构内容、兼容策略、已知未处理项、测试结果

Git 提交策略应遵循分阶段提交，而不是把所有修改压成一次提交。推荐至少区分为样式拆分、脚本拆分、数据抽离、文档补充等提交。

## 10. 不纳入本次范围的事项

以下内容明确不属于本次设计范围：

- Vue / React / Svelte / Angular 等框架接入
- Vite 或其它构建工具初始化
- TypeScript 引入
- npm 包安装
- 真实后端接口
- 真实微信登录
- 真实 AI API
- 微信小程序正式工程
- 大规模 UI 改版
- 业务逻辑重写

## 11. 设计结论

本次推荐采用“兼容优先的静态原型拆分重构”方案：

在不改变产品表现的前提下，把 `index.html` 中的样式、脚本和结构化内容拆分为 CSS、JavaScript 和 JSON 文件，保留现有 DOM 标识和内联事件调用方式，通过 `app.js` 统一初始化并做全局兼容暴露，确保项目仍可通过静态服务器直接运行，并为下一阶段继续迭代打下维护基础。
