# 学的是史 Task 0.5：测试基线与 CHANGELOG 设计

## 1. 背景与目标

`Task 0.1` 到 `Task 0.4` 已经完成了：

- 仓库现状基线梳理
- 占位文案与 `innerHTML` 审计
- `src/js` 动态渲染加固
- 数据校验脚本 `scripts/validate-data.js`

在进入 Phase 1 的 adapter 建设之前，需要把“当前仓库到底是什么状态”用可复查的方式固定下来。

Phase 1 计划中的 `Task 0.5` 要求：

1. 运行 `npx vitest run --environment jsdom`
2. 运行 `node scripts/validate-data.js`
3. 建立 `CHANGELOG.md`

因此本次任务的目标不是修复失败项，而是建立一份事实性的、可追溯的基线记录。

## 2. 设计范围

### 2.1 本次范围内

本次任务包含以下内容：

1. 运行当前测试命令
2. 运行当前数据校验命令
3. 新建 `CHANGELOG.md`
4. 在 `CHANGELOG.md` 中记录当前结果摘要
5. 提交 `CHANGELOG.md`

### 2.2 明确不在本次范围内

以下内容不属于本次任务：

- 修复任何测试失败
- 修复任何数据错误
- 修改前端逻辑以让测试变绿
- 修改 `src/data/*.json`
- 修改测试代码以“美化”结果
- 调整本轮之外的实施计划

本轮只记录现状，不改变现状。

## 3. 方案选择

### 3.1 选定方案

本次采用：**事实型基线记录方案**。

具体做法：

1. 运行计划要求的命令
2. 原样观察结果
3. 按类别整理为简洁摘要
4. 把结论写入 `CHANGELOG.md`

### 3.2 选择理由

该方案最适合当前阶段：

- 符合 `Task 0.5` 的原始目标
- 不把“记录问题”和“解决问题”混在一起
- 能为后续修复提供稳定对照
- 便于后续比较“某个任务是否改善了基线”

### 3.3 不采用的方案

#### 方案 A：先修若干失败再写基线

这会让“当前基线”失真，也会模糊 `Task 0.5` 的边界，因此不采用。

#### 方案 B：只保留命令原始全文输出

虽然最忠实，但可读性差，不利于后续快速回顾，因此不采用。应保留摘要，而不是把终端全文塞进文档。

## 4. 输出文件设计

### 4.1 输出文件

- 新建：`CHANGELOG.md`

### 4.2 文件定位

`CHANGELOG.md` 位于项目根目录，用于记录阶段性基线与重要变更。

本轮先建立第一条与 Phase 1 基线相关的记录。

## 5. 数据来源设计

### 5.1 测试基线来源

测试基线来自以下命令：

```bash
npx vitest run --environment jsdom
```

记录内容应包括：

- 测试文件总数
- 通过数量
- 失败数量
- 测试总数
- 失败测试数
- 失败项所属文件
- 每类失败的大致原因

### 5.2 数据校验基线来源

数据基线来自以下命令：

```bash
node scripts/validate-data.js
```

记录内容应包括：

- `OK / WARN / ERROR` 汇总
- `WARN` 的来源类别
- `ERROR` 的来源类别

## 6. CHANGELOG 内容设计

### 6.1 记录风格

`CHANGELOG.md` 采用事实型描述，不做主观修饰。

文案应避免：

- “已解决”
- “待后续优化”
- “计划之后修”
- “问题不大”

因为本轮不是问题管理，而是状态记录。

### 6.2 章节结构

建议至少包含以下结构：

1. 文档标题
2. `2026-06-10` 基线条目
3. 测试基线摘要
4. 数据校验基线摘要
5. 当前已知基线说明

### 6.3 测试基线摘要内容

根据当前实际运行结果，测试基线应记录：

- `12` 个测试文件
- `9` 个通过
- `3` 个失败
- `36` 个测试
- `32` 个通过
- `4` 个失败

并按失败类别概括为：

- `tests/app-static-data.test.js`
  - `app.js` 尚未接入梗图、反馈类型、热点文章、讨论区、个人菜单等静态数据渲染
- `tests/film.test.js`
  - `app.js` 尚未接入影视数据和榜单数据初始化
- `tests/resources-structure.test.js`
  - `resources/images/...` 目录骨架未满足测试预期

### 6.4 数据校验摘要内容

根据当前实际运行结果，数据基线应记录：

- `13 OK`
- `2 WARN`
- `20 ERROR`

并按类别概括为：

- `WARN`
  - `people.json` 当前为 `centers` 结构，因此跳过计划中的 `id/relations` 校验
  - `questions.json` 当前不存在，因此专项校验跳过
- `ERROR`
  - 全部来自 `nouns.json`
  - 具体表现为：
    - 缺少 `dynasty`
    - 缺少 `category`
    - `related` 指向不存在的名词

### 6.5 已知说明内容

在摘要后增加一小节“当前已知基线说明”，仅用于帮助后续阅读者理解结果，不包含整改承诺。

该说明可以包含：

- 失败和告警代表的是“当前仓库现状”
- 本次记录时未做修复
- 后续任务应以此作为对照基线

## 7. 文案边界设计

### 7.1 可以写的内容

可以写：

- 命令
- 结果数字
- 失败分类
- 告警来源
- 事实性说明

### 7.2 不应写的内容

不应写：

- 具体修复方案
- 优先级排序
- 负责人与时间安排
- “下一步必须做什么”的项目管理话术

这些属于后续任务设计，不属于本轮 changelog 基线。

## 8. 一致性规则

### 8.1 与终端结果一致

`CHANGELOG.md` 中记录的数字必须与本轮命令实际输出一致。

### 8.2 与 `Task 0.5` 一致

只记录 `Task 0.5` 明确要求的两类结果：

- 测试基线
- 数据校验基线

### 8.3 不隐瞒失败

失败和错误必须明确写出，不能只记录通过项。

## 9. 验收标准

当以下条件全部满足时，本次任务视为完成：

1. `CHANGELOG.md` 已创建
2. `CHANGELOG.md` 中已记录 `npx vitest run --environment jsdom` 的当前基线
3. `CHANGELOG.md` 中已记录 `node scripts/validate-data.js` 的当前基线
4. 文案保持事实性，没有混入修复实现
5. 仅提交 `CHANGELOG.md`

## 10. 后续衔接

本轮完成后，`CHANGELOG.md` 可作为后续任务的对照基线，例如：

- 修复 `app.js` 静态数据接线后，比较测试变化
- 修复 `nouns.json` 数据问题后，比较数据校验变化
- 完成资源目录整理后，比较资源结构测试变化

这些内容仅说明基线的用途，不构成当前任务的额外范围。
